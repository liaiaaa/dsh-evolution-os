### 0.2 关键发现

> 本章是本文档最重要的部分。每条都写明"这对方案意味着什么"。

#### 关键发现 1：记忆错误的产生阶段

经 Phase 1.5-C-2 逐条溯源核对：**57 条记忆中约 12% 存在错误**，其中 **3 条「原文即错」**（作业与 AI、E 盘绝对化、字数偏好）、**4 条「疑似过度归纳」**。

**错误产生于「写入阶段」而非整理阶段。**

- **归因**：原 `SKILL.md` 第 22 行"学到新事实就写回"**无用户确认门槛**。
- **含义**：记忆系统的核心风险不是"记得少"，而是"**记错了还一直用**"。错误记忆比缺失记忆危害更大，因为它会**主动误导** Agent 的决策——缺失只会让 Agent 多问一句，错误会让它自信地做错。

#### 关键发现 2：三类失效机制

| 机制 | 实例 |
|---|---|
| **绝对化** | 用户说"尽量放 E 盘" → 写成"绝不写 C 盘" |
| **固化** | 一次指定 200 字 → 写成"偏好精确字数" |
| **反转/错位** | 某门课"不能借助 AI" → 写成"用户要求作业独立完成" |

**含义**：LLM 事实抽取**天生会去掉限定词、把特例一般化**。这不是配置问题，是**固有缺陷**，只能靠"写入前确认"缓解。

#### 关键发现 3：mem0 会改写写入的 fact

mem0 内部用 LLM **重新表述** fact。实测：写入"优先 E 盘；确有必要写 C 盘需先确认"，mem0 存储为 `...is only permitted after explicit confirmation`（**强度被提升**）。

**含义**：MCP 层的"保留限定词"规则**管不了 mem0 内部**。回读确认只能**发现**偏差，不能**阻止**偏差。已列为已知限制。

#### 关键发现 4：嵌入式 Qdrant 不支持并发（官方确认）

实测错误原文提示"改用 Qdrant server 才支持并发访问"。**并行开 2 个 MCP Agent 时，后启动者读不到共享记忆。**

**含义**：这是**设计限制，非配置问题**。经评估用户使用模式（通常 1–2 个 Agent 同时使用）后可接受，因此**决定不迁移到 `qdrant.exe` 服务**，将其列为已知限制。

**迁移的成本**：新增常驻依赖 + **忘记启动时全部 Agent 失效**（一个需要用户每天记得开的服务，比偶发的锁冲突更糟）。

#### 关键发现 5：四个 Agent 的记忆机制各不相同

| Agent | 治理入口 | 加载方式 | 治理方式 |
|---|---|---|---|
| **DSH** | `mem0-memory` Skill | 热加载 | 改 `SKILL.md` |
| **WorkBuddy** | `MEMORY.md` | 每次会话注入 | 追加协议章节 |
| **MiMO** | Skill + `AGENTS.md` | Skill **不热加载**；AGENTS 必载 | 改 Skill + 建双份 `AGENTS.md` |
| **豆包** | 长期偏好接口（约 50 字/条） | 每次会话注入 | **无法写入复杂规则，只能读取 Obsidian 文件** |

**含义**：**不存在"统一配置一次就全部生效"的方案。每个 Agent 都要单独适配。**

豆包是四者中**唯一无法治理的**，它的角色被限定为"**读取偏好**"，不参与记忆写入。

#### 关键发现 6：`list_memories` 的隔离缺陷

`list_memories` **若不传 `agent_id`，会一并返回 `agent_id` 非空的条目**。这意味着本该"agent 级私有"的记忆会出现在所有 Agent 的检索结果中。

**含义**：当前的 `agent_id` 隔离**不可靠**，**不应依赖它存放私密内容**。

#### 关键发现 7：治理层的实际落地状态

**已落地**：
- **DSH**：`%USERPROFILE%\.dsh\skills\mem0-memory\SKILL.md` —— A/B/C 分级 + 自检 4 问 + 冲突处理 + 回读确认，**实测热加载生效**。
- **WorkBuddy**：`%USERPROFILE%\.workbuddy\MEMORY.md` —— 追加「共享记忆协议（DSH Evolution OS V1.3）」章节，含分级、自检 4 问、其他约束、已知限制。
- **MiMO**：Skill（B 级候选写入 `knowledge\Inbox\from-mimo.md`）+ `AGENTS.md`（项目级 + 用户级双份）。

**⏳ 未完成**：
- **豆包**：无法写入复杂规则（见关键发现 8）。
- ~~**MiMO 的全局 `MEMORY.md`** 仍保留旧规则~~ → **已于 Phase 3-E2 处理完毕**（该文件与 `projects\global\MEMORY.md` 的旧规则已整节替换为 V1.3 口径，并加入优先级声明）。

#### 关键发现 8：豆包未真正接入共享 mem0（物理验证）

**物理证据**（写入测试后逐项核对）：

| 证据 | 结果 |
|---|---|
| `mem0.db` 与 `storage.sqlite` 时间戳 | **未变**，且早于写入动作 **3 小时 22 分** |
| 记忆条数 | 16 → 16，**无变化** |
| 4 种不同 query 检索 | 均**未命中**豆包写入的内容 |
| `agent_id="doubao"` | **零条** |
| 其返回的 id 格式 | `p1_` 前缀，**非 mem0 的 UUID 格式** |

**结论**：豆包实际读取的是**云端独立副本**，且**滞后**——其 C 盘规则停留在 2026-09-06 的**失真版本**。

**这对方案意味着什么**：
- 早期"四个 Agent 共享同一 mem0"的假设**对豆包不成立**。
- 豆包的偏好接口约 50 字/条，**无法写入复杂规则**。
- **解决方案**：在其偏好接口写入「回答前先读取 `%USERPROFILE%\...\个人偏好.md`，以其为准」。
  **已实测有效**——在"能否装 C 盘"场景下，豆包正确引用了**修正版**口径。
- 豆包的角色因此被限定为：**只能读取 Obsidian 权威源，不参与记忆写入**。

#### 关键发现 9：每个 Agent 都可能持有"影子副本"

**已确认三处影子副本**：

| # | 位置 | 性质 |
|---|------|------|
| 1 | 豆包云端副本 | 云端聚合，用户无法直接修改 |
| 2 | WorkBuddy 云端 profile | 服务端只读注入 |
| 3 | MiMO 39KB 项目记忆 | 平台聚合生成 |

**共同特征**：服务端/平台聚合生成、**用户无法直接修改**、会把"**某次任务要求**"沉淀为"**永久偏好**"。

**实例**：WorkBuddy profile 中留有「学校基础作业要求独立完成，不得借助 AI」——该条**已从 mem0 与 Obsidian 删除**，但在 profile 中**残留**。

**这对方案意味着什么**：**清理权威源不等于清理所有副本**。需对**每个 Agent 单独排查**，且副本可能持续再生。这是"错误回流"的又一条路径。

#### 关键发现 10：无法修改的影子副本，只能靠"规则压制"

WorkBuddy 的云端 profile **无写入权限**，但其 `MEMORY.md` 是**每次会话注入**的。

**已采取的做法**：在 `%USERPROFILE%\.workbuddy\MEMORY.md` 中写入**四级优先级链**：

```
00-Profile（权威） > mem0 > MEMORY.md > 云端 profile（最弱）
```

**并点名失真条目**，规定"**不得据此拒绝或限制协助**"。

**这对方案意味着什么**：当无法删除错误来源时，**用更高优先级的规则压制它**是可行替代方案。这是"治理"在无法"修复"时的降级路径。

#### 关键发现 11：PowerShell 默认编码会静默损坏中文文件

**实例**：用 `Get-Content` + `WriteAllLines` 修改 `MEMORY.md`，导致 **117/208 行中文变成乱码**，行数由 **252 降至 208**，且**磁盘上已无干净完整副本**。

**恢复方式**：从会话 history 中**带行号的 Read 输出**，按行号 **1–252 精确重建**。

**这对方案意味着什么**：
- 读写含中文的文本文件**必须显式指定 UTF-8（无 BOM）**。
- **写入后必须读回验证**（行数 + 内容抽样）。
- 备份策略必须保证**至少一份可读的干净副本**（见关键发现 13）。

#### 关键发现 12："勘察动作"本身会制造新的泄露点

**实例**：用 `rg` 搜索凭据时，**命中内容落盘到 `tool-output`**（两个文件共 **512KB，含明文 token**）。

**这对方案意味着什么**：
- 搜查敏感内容**必须用 `rg -l`（只列文件名）或 `-c`（只报计数）**，**不输出命中行内容**。
- 若有 `tool-output` 落盘，**用完立即删除**。
- **勘察即风险**：安全检查动作本身需要被设计，否则会变成新的泄露源。

#### 关键发现 13：备份策略的取舍

**曾经的做法**：为避免凭据落入备份，采用"**只记哈希不记原文**"。

**后果**：在编码事故（关键发现 11）中**失去了恢复源**——因为没有原文可恢复。

**这对方案意味着什么**：**正确做法是"备份原文 + 立即对备份脱敏"，而非跳过备份。**
"不备份"看似更安全，实际把可恢复性降为零，在真正需要时无法挽回。

#### 关键发现 14：含密文件的处理边界

**已成功处理**：`longcat` 历史代理 key（32 位）——
- 用户在**服务商侧吊销**；
- 清理 **4 处本地副本**；
- 扩展扫描确认 **0 完整副本**。

**边界守护**：**未触碰** `%USERPROFILE%\.dsh\.credentials.yaml`（DSH 正式凭据库）。

**这对方案意味着什么**：凭据处理应遵循「**先吊销 → 再清理 → 后验证**」的顺序。吊销优先，因为清理总有遗漏可能；且**必须明确边界**，不越界触碰正式凭据库。

#### 关键发现 15：`.git` 目录不等于 Git 仓库

**实例**：`<示例路径>\.git` **仅含一个 project-id 文件**，无 `HEAD`/`objects`/`refs`，**不是有效仓库**。

**这对方案意味着什么**：判断"是否在版本控制内"**必须实际执行 `git log` / `git remote`**，而非只看 `.git` 目录是否存在。仅凭目录存在做判断会得出错误结论。

#### 关键发现 16：清理不是免疫——系统会自己「长回来」

**这是本方案最深刻的结构性发现。**

**事实**：Phase 1.5 把 mem0 从 57 条清理到 17 条。**两天后复查，已涨回 40 条。**

**涨回来的是什么**：竞赛报名状态、获奖记录、硬件资产清单、学历信息、个人生活信息（常用软件、AI 绘画风格）——
**正是当初清理掉的那几类。**

**为什么会涨回来**：

| 环节 | 状态 |
|------|------|
| 写入路径 | ✅ 有（A/B/C 分级 + 自检 4 问 + 回读确认） |
| **免疫系统** | ❌ **无** |

**具体缺口**：

1. **门禁写在 Skill 里，而 Skill 不一定被加载** —— MiMO 的 Skill 不热加载，规则形同虚设。
2. **只有写入规则，没有定期审计** —— 记忆可以静默增长，只有人工想起时才被发现。
3. **A 级判定被放宽** —— "项目状态"被当作"用户事实"写入，因为它确实"是事实"，但它不是**跨会话复用的稳定偏好**。
4. **权威源迁走内容后，mem0 原件未同步删除** —— `个人偏好.md` 已把个人生活条目迁出，mem0 里却还留着。

**这对方案意味着什么**：

> **一次性清理 ≠ 持续免疫。** 一个只有写入路径、没有审计机制的记忆系统，
> 会以可预测的速度劣化——**清理后的干净状态是暂时的，漂移才是默认状态。**

**由此确立的三条设计原则**：

1. **审计必须是可执行的脚本，不是文档里的规矩** —— `tools\drift_check.py`，只读、幂等、可重复运行。
2. **门禁必须放在"必载"位置** —— 项目 `AGENTS.md`（每会话注入），而非仅放在 Skill 里。
3. **必须有"负面记录"** —— `00-Profile\拒绝清单.md` 记录已拒绝的候选，防止反复提议同类内容。

**量化证据**：40 条中 **26 条越界**（身份 12 / 获奖 5 / 项目状态 3 / 个人生活 2 / 时效性 1 / 限定词失真 3），
真正的 A 级偏好只有 **14 条**。即 **65% 的记忆是噪声**——它会稀释检索精度，让"记忆系统"在体感上变得**无效**。

## 2. 目标与边界

### 目标
让 DSH、豆包、WorkBuddy、MiMO 在更换入口后，仍能理解用户的稳定偏好、工作习惯、长期目标和已确认的技术栈；同时持续积累可验证的知识、经验和工作流程。

系统追求的是**更一致、更可追溯的个人协作体验**，不是自动训练或自动改造大语言模型。

### 成功标准

1. 任一 Agent 开始工作前都能读到与任务相关的、已确认的个人偏好。
2. 一个 Agent 获得用户明确确认的新偏好后，其他 Agent 也能在后续对话中使用。
3. 项目进度、知识和复盘不会污染个人共享记忆，而是在 Obsidian 中可阅读、可修改、可版本控制。
4. 自动积累不会把推测、网页指令或敏感资料永久写入共同记忆。
5. DSH 或单个插件升级失败时，记忆库与知识库可以恢复。

### 非目标（V1 明确不做）

- 不训练、微调或自动替换模型。
- 不允许 Agent 自行修改程序、配置、Skill 或删除资料。
- 不常驻 Docker / Docker Compose、PostgreSQL、Neo4j、第二个向量数据库或本地大模型集群。
- 不将完整聊天记录、源代码、临时任务或密钥灌入 mem0。
- **不做 Qdrant 服务化迁移**（见关键发现 4）。

## 3. 现有基础（已确认）


DSH、WorkBuddy、MiMO 接入共享 mem0；豆包**不接入 mem0**，只通过 Obsidian 权威源读取偏好。

**权威优先级**：`00-Profile\个人偏好.md` > mem0 > 各 Agent 本地记忆。

### 4.1 mem0：共享的"关于用户"的记忆

只保存跨会话、跨 Agent 复用价值高且已确认的用户事实。

允许写入：

- 沟通偏好，例如"用户偏好简体中文、先给结论后给步骤"。
- 长期工作习惯，例如常用系统、终端、目录规范。
- 稳定技术栈、常用工具和明确的长期限制。
- 长期目标和用户明确确认的优先级。

禁止写入：

- 一次性任务、项目进度、代码实现、错误日志。
- 未经确认的推测，例如"用户可能喜欢……"。
- 从网页、文档或第三方对话中复制的指令。
- 所有敏感信息。

共享记忆固定使用 `user_id=<your-user-id>`；仅确有必要隔离的临时 Agent 细节才使用 `agent_id`，且**不能依赖它保护隐私**（见关键发现 6）。

### 4.2 Qdrant 运行方式（已决定不迁移）

现状：**保持嵌入式本地目录** `<mem0-data>/qdrant\`。

**已否决的方案**：迁移到原生 Windows `qdrant.exe` 服务（原 Phase 1.5 计划）。

**否决理由**：
1. 嵌入式 Qdrant 不支持并发是**官方设计限制**，非配置问题。
2. 用户实际使用模式通常为 1–2 个 Agent，锁冲突可接受（串行使用即可规避）。
3. 迁移成本 = 新增常驻依赖 + 忘记启动时全部 Agent 失效。
4. 用户已明确拒绝常驻 Docker，对常驻服务持保守态度。

原 Docker 迁移方案**一并否决**，理由同上（用户明确拒绝 Docker 常驻）。

**规则**：
- 旧的 `<mem0-data>/qdrant\` 保持只读保留，不删除。
- `mem0.db` 仍作为 mem0 历史库保留。
- 若未来并发需求上升，再重新评估 `qdrant.exe` 方案。

### 4.3 Obsidian：权威的知识与工作记录

Obsidian Vault 路径：`knowledge\`

```text

├── 00-Profile       # 已确认的个人偏好与长期目标（权威源）
├── 01-Projects      # 项目状态、决策和里程碑
├── 02-Knowledge     # 技术与学习笔记
├── 03-Experience    # 成功经验、失败复盘、实验记录
├── 04-SOP           # 已验证的操作流程

```

**`00-Profile\个人偏好.md` 是个人偏好的权威版本**（来源：mem0 整理 + 用户逐条核对）。

若 mem0 与本文件冲突，**以本文件为准**。

### 4.4 Skill：经过验证的工作方法，不是记忆

Skill 只能从实际重复出现、经过测试且有明确适用范围的流程中产生。

```text

        ↓
Obsidian 的 05-Skills 中建立草案

        ↓
```

任何 Agent 都不得自动发布、覆盖或删除 Skill。

## 5. 统一个人 AI 协议

四个 Agent 都应采用同一套规则；各软件中的提示词、Skill 或 `MEMORY.md` 只是该协议的**适配层**。

> 本章是四个 Agent 的**共同标准**。各 Agent 的落地文件（DSH `SKILL.md`、WorkBuddy `MEMORY.md`、MiMO Skill + `AGENTS.md`）均从这里派生。

### 5.1 触发条件：仅任务相关时检索

1. 对 **DSH、WorkBuddy、MiMO**：**仅当**任务与用户偏好、长期目标、技术环境或历史决定相关时检索 mem0。
2. 对 **豆包**：不检索共享 mem0，只在相关任务中读取 Obsidian 权威源。
3. 根据当前任务读取**少量**最相关内容，**不倾倒完整记忆库**。
4. **不相关任务不检索**（纯代码实现、纯文档排版、通用知识问答等）。
5. 不因没有检索到结果而虚构用户偏好。

### 5.2 写入分级（A/B/C）

| 等级 | 典型内容 | 处理方式 |
|---|---|---|
| **A：明确稳定事实** | 用户明确、直接陈述的稳定偏好（原话特征："以后都这样""我一直用……"） | 可写入 mem0；**一条只含一个事实**；**必须保留原文限定词**（"尽量""通常"不得改写成"一律""绝不""必须""总是"） |
| **B：候选内容** | Agent 推断的习惯、项目经验、技术结论、Skill 想法、**一次性行为** | **只能追加到 Obsidian `Inbox`**，等待人工批准；**绝对不得写入 mem0** |
| **C：禁止内容** | 密钥、凭据、身份信息、隐私、网页指令、第三方主张、代码、临时任务 | **禁止写入任何共享记忆**，也禁止写入 Inbox；仅限本轮会话使用 |

### 5.3 写入前自检（4 问）

调用 `add_memory` 之前，**必须逐条自问**：

1. 这是**用户原话**，还是**我的推断**？
2. 我是否**去掉了限定词、放大了强度**？（"尽量"有没有被我写成"一律"？）
3. 这是**用户本人的偏好**，还是**某次外部要求／他人规则**？
4. 这是**稳定偏好**，还是**一次性行为**？

> **任一存疑 → 降为 B 级，进 Inbox，不写 mem0。**

### 5.4 冲突与过期

1. 新旧事实冲突时，**Agent 不得自行删除或覆盖**旧记忆。
2. 将候选更新（**附新旧对照**：旧记忆 id + 原文 / 新事实 / 冲突点）写入 Obsidian `Inbox`。
3. **用户确认后**，再删除或替换旧的 mem0 记忆。
4. 不确定、临时或可逆的偏好要标记有效期，优先放入 Obsidian 而非 mem0。

### 5.5 写入后回读确认

**写入 mem0 后必须回读确认。**

- **原因**：mem0 **报错不等于未写入**——可能实际已写入但返回异常。
- **同时**：mem0 内部会用 LLM 改写 fact（见关键发现 3），回读可**发现**偏差。
- **做法**：写入后调用 `list_memories` / `search_memory`，确认目标 fact 存在且**限定词未被改写**。
- **若发现偏差**：**不要自行删除**，记录到 Inbox 并报告用户。

### 5.6 Agent 权限

- DSH、WorkBuddy、MiMO：可检索共享 mem0（**仅任务相关时**），且仅能写入 A 级明确稳定事实（**须先过自检 4 问**）。
- 豆包：**不接入共享 mem0**，只读 Obsidian 权威源；不写 mem0 或 Inbox。
- DSH、WorkBuddy、MiMO：可向各自 Obsidian `Inbox` 缓冲提交 B 级候选，**不得自行移入正式目录**。
- 所有 Agent：**不得自行 `delete_memory`**；仅在用户明确指示并给出具体 id 时使用。
- 只有用户：批准、发布、删除共享事实和 Skill。

## 10. 已知限制

> 这些是**已确认的架构固有局限**，不是待修复的 bug。部分无法通过配置修复。

### 限制 1：mem0 会改写 fact 的限定词，**改写方向不可预测**

mem0 内部会用 LLM 重新表述写入的 fact。**改写方向不可预测**：

- 实测中有一次**弱限定词被强化**（「尽量」→ `only permitted after`）；
- 另一次则**完整保留**（「优先」→ `prefers ... over`）。

因此**不能假设写入安全，也不能假设必然被改坏**。回读确认只能**发现**偏差，不能**阻止**偏差。

**唯一可靠做法是：每次写入后必须回读确认，逐词比对限定词。**

**结论：mem0 中的事实强度可能与用户原意不一致；Obsidian 为权威源。**

> 该限制已由两次实测证实（Phase 1.5-E、Phase 2-C-D）。

### 限制 2：无法用技术手段区分"用户真实强偏好"与"被强化的表述"

诸如"不得编造"这类表述，可能确实是用户明确要求，也可能是 Agent 写入时强化出来的。二者在文本上**不可区分**。只能依赖 **Agent 判断 + 用户定期抽查**。

**这是当前架构的固有局限，不是可通过配置修复的问题。**

### 限制 3：嵌入式 Qdrant 不支持并发

同时使用多个 MCP Agent 时，**后启动者读不到共享记忆**（报错提示需改用 Qdrant server）。这是官方设计限制。

**缓解**：串行使用 Agent；或接受偶发读取失败并稍后重试。

### 限制 4：豆包无法被治理

豆包的长期偏好接口约 50 字/条，**无法写入复杂规则**。它的角色被限定为**只能读取 Obsidian 文件**，不参与记忆写入。

**含义**：四 Agent 中有一个无法纳入统一协议，协议覆盖率为 3/4。

### 限制 5：WorkBuddy 存在云端 profile

WorkBuddy 有云端 profile 与本地 `MEMORY.md` **两套独立记忆**，用户**无法控制云端部分**。未来可能产生与本地协议冲突的偏好。

**缓解**：已在 `MEMORY.md` 中声明"若三者冲突，以 `00-Profile\个人偏好.md` 为准"。

### 限制 6：`agent_id` 隔离不可靠

`list_memories` 不传 `agent_id` 时会返回 `agent_id` 非空的条目。**不应依赖 `agent_id` 存放私密内容。**

### 限制 7：MiMO 全局 `MEMORY.md` 仍保留旧规则（待清理）

`%USERPROFILE%\.local\share\mimocode\memory\global\MEMORY.md` 目前仍写着"冲突写入时说明最新状态、mem0 会自动去重更新"——这与 V1.3 的"**不得自行删除或覆盖**"相冲突。

> ⚠️ **本条已于 2026-09-12（Phase 3-E2）处理完毕**：该文件与 `projects\global\MEMORY.md` 的旧规则已整节替换为 V1.3 口径，并加入优先级声明。**此项限制已解除**，保留于此仅作历史记录。

### 限制 8：豆包无法写入共享 mem0，只能读取 Obsidian 权威源

经物理验证，豆包**未接入共享 mem0**（见关键发现 8）。其偏好接口约 50 字/条，无法承载复杂规则。

**后果**：豆包的偏好**只能靠人工维护其 50 字指引**，且其云端副本会滞后于权威源。

**缓解**：已在豆包偏好接口写入「回答前先读取 `00-Profile\个人偏好.md`，以其为准」，**实测有效**。

### 限制 9：云端 profile 与平台记忆无法直接修改，只能靠规则层压制，且会再生

WorkBuddy 云端 profile 与 MiMO 项目记忆**均无直接写入权限**。只能通过各自**每次会话注入的规则层**（`MEMORY.md` / `AGENTS.md`）压制（见关键发现 10）。

**且 profile 会持续生成新的失真条目** —— 平台会把"某次任务要求"沉淀为"永久偏好"。

**后果**：这是一项**长期维护负担**，**需定期复查**，不是一次性修复。

### 限制 10：四 Agent 不存在"配置一次即全部生效"的统一方案

四个 Agent 的记忆机制**各不相同**（热加载 Skill / 会话注入 MEMORY.md / 不热加载 Skill + 必载 AGENTS.md / 50 字偏好接口）。

**后果**：每新增一条协议规则，**都需要在四处分别适配**；且各自的生效条件不同（有的需新开会话）。

**这是当前架构的固有成本**，除非改变 Agent 接入方式，否则无法消除。

### 限制 11：记忆系统会「自己长回来」——漂移是默认状态

**Phase 1.5 清理后两天，mem0 由 17 条涨回 40 条**（见关键发现 16）。65% 是噪声。

**根因**：系统只有「写入路径」，没有「免疫系统」。写入规则能约束**单次写入的质量**，
但无法阻止**记忆总量的静默增长**。

**后果**：

- 清理后的干净状态是**暂时的**；漂移才是默认状态。
- 噪声会**稀释检索精度**，让记忆系统在体感上变得**无效**——这不是错觉，是信号被淹没。
- **审计必须由脚本定期执行**，不能依赖"想起来才查"。

**缓解**：`tools\drift_check.py` + 每周审计节奏 + 必载门禁 + 拒绝清单（第 8 节）。
**但这不是一次性修复，而是长期运维负担。**
